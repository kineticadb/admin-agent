# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What This Is

An autonomous diagnostic agent for Kinetica databases, built with the Claude Agent SDK (`@anthropic-ai/claude-agent-sdk`). The agent connects to a live Kinetica instance, investigates issues using 23 live MCP tools (16 diagnostic + 4 mutation + save_report + confirm_save_report + alter_table_columns) — plus 6 file-backed bundle tools when a support bundle is in play, 4 observability tools whenever a Prometheus/Loki stats stack is reachable, and `kinetica_knowledge_read`, which serves the knowledge corpus on demand in every session (**34 total**) — and produces structured markdown reports.

It also supports **offline support-bundle analysis** (`--bundle=<dir>`): it can diagnose from an extracted `gpudb_sysinfo` bundle (per-rank logs, gpudb.conf, host diagnostics) — the logs being evidence the live endpoints can't expose. Live connection and bundle are **composable capabilities**, not exclusive modes: a session can have a live connection, an attached bundle, or both (so the agent can cross-check frozen bundle evidence against current live state). A bundle can be attached at startup (`--bundle`) or mid-conversation (`kinetica_load_bundle`). See Offline Bundle Mode below.

## Architecture

### Startup Flow

`cli/index.ts` → `--logout` early exit via `auth/logout.ts` (if flag) → `--version` early exit via `cli/version.ts` `getVersion()` (walks up to `package.json`, works in both dev and bundled mode) → `--model=<name>` parsed and validated against `SUPPORTED_MODELS` (unknown values exit with code 1 before any side effects) → `session/env-file.ts` `loadEnvFile()` (`.env` → `process.env`, shell vars win, empty values skipped) → `cli/banner.ts` `printBanner()` (gradient logo + version to stderr) → `cli/select-model.ts` `selectModel()` (interactive model picker — shown **only** when no `--model` flag was given and the terminal is interactive; non-interactive runs and an explicit `--model` both skip it; the choice is never persisted, so the picker reappears every interactive launch) → resolve `effectiveModel = model ?? DEFAULT_AGENT_MODEL` and write the dim `Model: <name>` line to stderr → `auth/preflight.ts` `authenticateAnthropic()` (Anthropic auth — API key check or OAuth login via lightweight SDK query; fails fast if non-interactive with no API key) → `session/verify.ts` `connectWithRetry()` orchestrates: `session/collect.ts` `collectCredentials()` (Kinetica credentials from env with saved-connection confirmation, or interactive prompt) → `session/resolve-url.ts` `resolveUrl()` (adds `https://` or `http://` if missing, probing the host) → `session/KineticaSession.ts` (closure-based session, 30s request timeout) → verify connectivity + extract Kinetica version (up to 3 retries; 401/403 triggers credential re-prompt via `repromptCredentials()`, up to 2 cycles) → on success, `offerSaveCredentials()` writes URL/user (+ stats host) to `.env` if any field was interactively prompted → `cli/observability-setup.ts` `setupObservability()` (resolves Prometheus/Loki from the collected host, else `gpudb.conf`; prints one dim `Observability: …` line; never blocks) → `agent/run-agent.ts` (agent loop with version + model override + observability client)

**Degraded mode fallback:** After 3 failed attempts to reach port 9191, `connectWithRetry()` probes the host manager on port 9300 via `probeHostManager()`. If 9300 responds, the agent starts in degraded mode (`degraded: true`) — schema discovery is skipped, the system prompt includes a DEGRADED MODE section guiding the agent to use only `kinetica_host_manager_status`, and the welcome message warns the operator. Version is extracted from the HM response. If both 9191 and 9300 are unreachable, exits with code 1.

**Offline bundle entry (`--bundle=<dir>`):** When `--bundle` is given, `cli/index.ts` branches **before** `connectWithRetry()` — it skips interactive Kinetica credential collection (Anthropic auth still runs). It calls `bundle/verify-bundle.ts` `verifyBundle()`, which validates the directory (fails fast with an extract-first message if handed a `.tgz`), builds the `BundleSource`, detects the version, and reports an inventory + a `layout` verdict (`canonical | partial | unfamiliar`, warned on stderr when off-shape) + any missing-expected artifacts (non-fatal). It then attempts `connectBestEffort()` (env-only creds, no prompts, no exit) so the agent can also verify against the live system if it's reachable — the cluster is often down, in which case it continues bundle-only. The result is threaded into `runAgent(liveSession?, version, degraded, model, { …, bundleSource })`, where `version` is the **bundle's captured** version (via `chooseBundleSessionVersion()`, which prefers it over a reachable live cluster's — the live system may have been upgraded since capture, and version-quirk reasoning must follow the frozen evidence; a live/bundle version mismatch is warned on stderr). See Offline Bundle Mode below.

### Authentication (`auth/`)

Two Anthropic authentication methods: API key (via `ANTHROPIC_API_KEY` env var) and OAuth login (browser-based, same flow as `claude login`). Authentication runs **before** Kinetica credential collection — fail fast if no plausible auth path.

- **`preflight.ts`**: `authenticateAnthropic()` determines the auth method early in `main()`. API key path returns immediately. OAuth path creates a lightweight SDK query (never iterated — no API tokens consumed), probes for cached credentials via `accountInfo()` (reuses tokens from previous sessions), and only runs the full browser-based OAuth handshake if no cached credentials are found. Non-interactive terminals with no API key throw immediately with a clear error. The `--login` flag bypasses the cache probe and always triggers fresh OAuth.
- **`oauth-flow.ts`**: `resolveAuthentication()` drives the 3-step OAuth handshake via undeclared SDK methods (`claudeAuthenticate`, `claudeOAuthWaitForCompletion`). The `OAuthCapableQuery` interface type-asserts these runtime methods. Called by `preflight.ts` only when the cache probe fails. Graceful degradation on error — warns to stderr, returns result so the SDK can retry.
- **`open-browser.ts`**: Cross-platform browser opener (`open` on macOS, `xdg-open` on Linux, `cmd /c start` on Windows). Detached child process, never throws.
- **`logout.ts`**: `logout()` clears cached OAuth credentials by delegating to `claude auth logout`. Returns a `LogoutResult` with success/message. Never throws. SDK 0.3.x ships that CLI as a **native per-platform binary** (an os/cpu-gated optional dependency, `@anthropic-ai/claude-agent-sdk-<platform>-<arch>/claude`) rather than the 0.2.x bundled `cli.js`, so it is executed directly instead of under `process.execPath`. The SDK exports no resolver for it, so the exported pure helper `binaryCandidates(platform, arch, preferMusl)` mirrors the SDK's own candidate order (two candidates on Linux, since glibc/musl decide which optional dependency installed). Because `logout()` never throws, a resolution failure surfaces as a result message, not a crash — which is exactly why the 0.2→0.3 packaging change was invisible to both typecheck and the test suite. `auth/logout-packaging.test.ts` closes that blind spot: it mocks **nothing** and resolves against the real installed `node_modules`, so a future rename or relocation of the binary fails CI instead of a user's `--logout`. The mocked tests in `logout.test.ts` can't do this — they assert the candidate loop's shape against a fabricated tree, which is the same blind spot in miniature.

### Session Management (`session/`)

- **`env-file.ts`**: `.env` file loading and saving. `loadEnvFile()` synchronously reads `.env` at startup, populates `process.env` for keys not already set (shell vars always win), skips empty values so interactive prompts still trigger. `offerSaveCredentials(url, user, dir?, statsHost?)` offers to write `KINETICA_URL`, `KINETICA_USER` and (when supplied) `KINETICA_STATS_HOST` to `.env` after a successful interactive connection — password is never saved, and an existing `KINETICA_STATS_HOST` is left untouched when none was collected. Updates existing `.env` in-place (preserving comments and other vars) or creates from template. Pure helpers: `parseEnvContent()` (parses `.env` content to `ReadonlyMap`), `buildEnvContent()` (generates/updates `.env` content), and `upsertEnvValue()` (inserts or replaces a single `KEY=value` line, keeping an existing key in position so surrounding comments stay meaningful — deliberately separate from `buildEnvContent()`, which owns the URL/USER template). Never throws.
- **`resolve-url.ts`**: URL protocol resolution. `resolveUrl()` normalizes bare hostnames (e.g., `host1:9191`) by probing HTTPS first (3s timeout). If HTTPS fails and HTTP succeeds, the user is shown a red warning that credentials would travel in cleartext and asked to confirm interactively; declining returns `ok: false`. Non-interactive terminals refuse the fallback unconditionally. Setting `KINETICA_HTTPS_ONLY=1` refuses any fallback without prompting. Returns a discriminated union `ResolveUrlResult` (`ok: true` with resolved URL, or `ok: false` with error). Rejects unsupported schemes (ftp, ws). `hasProtocol()` is a pure helper for checking `http://`/`https://` prefix. Called by `connectWithRetry()` before creating the session.
- **`collect.ts`**: Credential collection. `collectCredentials()` returns `CollectResult` (`{ credentials, prompted }`) — the `prompted` set tracks which fields were interactively entered (`"url"` | `"user"` | `"statsHost"`), used downstream to decide whether to offer `.env` save. When both URL and user are available from env and the terminal is interactive, displays the saved connection and asks "Use saved connection?" (defaults to yes); declining re-prompts for all fields. `repromptCredentials()` always prompts for user + pass (ignores env), used on 401/403 auth failure. Also asks **"Prometheus/Loki host URL (e.g. http://statshost, blank if none):" immediately after the password**, populating `Credentials.statsHost` — see the Observability section for why this is collected rather than derived. That question is skipped on the "Use saved connection? (Y)" path, whose contract is to ask nothing: a blank answer cannot be remembered (`loadEnvFile` skips empty values so prompts still fire), so asking there would nag every launch of a cluster with no stats stack.
- **`verify.ts`**: `connectWithRetry()` orchestrates the full connection flow. On credential errors (401/403), detected by `isCredentialError()`, offers to re-prompt instead of blind retry — new credentials get a fresh retry counter. Limited to `MAX_REPROMPTS` (2) cycles. After successful connection (normal or degraded), calls `offerSaveCredentials()` if any field was interactively prompted or re-prompted. `ConnectResult` carries `statsHost` (from `collectCredentials`, or `readStatsHostEnv()` in `connectBestEffort`'s env-only path) so the CLI can hand it to `setupObservability` without re-reading anything.

### Agent Loop (`agent/run-agent.ts`)

Creates an in-process MCP server via `createSdkMcpServer()` with the composed tool set — `serverTools = liveTools + bundleTools + observabilityTools + knowledgeTools + confirm_save_report + save_report` (up to 34 in a live session: 16 diagnostic + 4 mutation + alter_table_columns + 6 bundle + 4 observability + knowledge_read + confirm_save_report + save_report; 13 in bundle-only mode, where no live tools are constructed but bundle, observability and knowledge tools remain) — then streams a `query()` call. Uses `makeInteractivePrompt()` — an async generator that yields user messages between agent turns, synchronized by a `TurnGate` (`agent/turn-gate.ts` — promise-based gate that prevents the prompt from appearing before the agent finishes its turn).

**Exports for eval reuse:** `MCP_SERVER_NAME`, `makeUserMessage()` (the `SDKUserMessage` envelope helper), `buildApprovalRegistry()` and `unqualifyToolName()` are exported from this module so the evals and the safety tests reuse the real construction rather than a copy. The former `ALLOWED_TOOL_NAMES` / `BUNDLE_` / `OBSERVABILITY_` / `KNOWLEDGE_ALLOWED_TOOL_NAMES` constants are **gone** — see Allowed tools below.

Agent configuration:

- **Model**: defaults to `"sonnet"` (SDK resolves shorthand to latest version); operator can override via `--model=<sonnet|haiku|opus|fable>` on the CLI, or — when no flag is given and the terminal is interactive — via the startup model picker (`cli/select-model.ts`, an `@inquirer/prompts` `select` defaulting to `sonnet`). Valid values come from `SUPPORTED_MODELS` in `agent/run-agent.ts` — both the CLI flag validator and the picker render from that tuple, so neither can drift. `MODEL_LABELS` in `select-model.ts` is typed `Record<AgentModel, string>`, so adding a model without a picker label is a typecheck error — as is adding one without a `MODEL_PRICING` entry or a `MODEL_IDS` entry.

  **The alias is resolved by the SDK's baked-in catalog, so upgrading the SDK can silently change which model runs.** Measured 2026-09-16: `@anthropic-ai/claude-agent-sdk` 0.2.80 mapped `sonnet` -> `claude-sonnet-4-6`; 0.3.273 maps it -> `claude-sonnet-5` (`latest_per_family` in the binary's hand-maintained model catalog). Nothing in this repo changed, no version string moved here, and the typecheck/test suites are model-blind — but every session and every eval switched models. When an SDK bump changes model-dependent behaviour, check the alias target before assuming a code regression, and treat the evals as the detector: they are the only thing here that exercises a real model.

  `MODEL_IDS` maps the CLI name to the string handed to the SDK. The SDK accepts "an alias or a full model ID" but its alias set is exactly `sonnet | opus | haiku`, so `fable` is passed as the full ID `claude-fable-5-1` while the other three stay aliases and keep being resolved to current by the SDK. Fable is Anthropic's most capable model, for long autonomous runs; it costs 2× Opus ($10/$50 per MTok vs $5/$25) and its cache reads are a published $0.25/MTok rather than the 0.1× ratio the others follow — which matters here because the cached system prompt is re-read every turn.

- **Fallback model**: `"haiku"` — automatic failover if primary model is unavailable
- **Thinking**: `{ type: "adaptive" }` — SDK decides when to use extended thinking
- **Allowed tools**: `allowedTools` is passed **EMPTY**, on purpose. A bare entry there auto-approves the tool _inside the SDK before `canUseTool` runs_, so it is a second, higher-priority copy of the approval decision. Which tools bypass the prompt is declared once, in the approval registry built by `buildApprovalRegistry()`: bundle + observability + knowledge tools always, plus `save_report` and `confirm_save_report` in every mode, plus the 16 diagnostics and `alter_table_columns` when a live session exists. Mutation tools are never registered, so they reach the gate and prompt.
- **Disallowed tools**: `Bash`, `Edit`, `Write`, `MultiEdit` — agent cannot modify files or run shell commands
- **`canUseTool` callback**: wires `createApprovalGate()` — mutation tools not in the allow-list trigger interactive y/n/explain approval prompt

  **On `CLAUDE_SDK_CAN_USE_TOOL_SHADOWED` (SDK 0.3.x), and the latent bug it exposed.** The SDK warns when a bare `allowedTools` entry auto-approves a tool before `canUseTool` runs. This agent used to list 19 tools there AND mark the same tools read-only in the approval registry — one decision written twice, with the SDK's copy winning. That hid a real defect: the registry is keyed on **bare** names (`kinetica_health_check`) while the gate is handed **qualified** ones (`mcp__kinetica-diagnostics__kinetica_health_check`), so `isReadOnlyTool` answered false for every live tool and the gate's read-only path was dead code. It never showed, because the allow-list meant the gate only ever saw mutation tools — which default-deny correctly either way. Trimming the allow-list without fixing the spelling would have prompted the operator for 16 read-only diagnostics. Both halves are fixed: `unqualifyToolName()` strips the prefix before the lookup, `save_report` and `alter_table_columns` are registered (they were allow-listed but absent from the registry), and `allowedTools` is now empty. Measured: the warning fires with a bare entry and does not fire with an empty list. The registry's default-deny is now a genuine backstop rather than unreachable code, and `agent/approval-wiring.test.ts` asserts the property end to end against the real composition — every read-only tool auto-allows without prompting, every mutation tool prompts, and an unknown tool is denied.

- **Budget**: configurable per-session cap, resolved `--max-budget` flag > `ADMIN_AGENT_MAX_BUDGET` env > `DEFAULT_MAX_BUDGET_USD` ($5.00) via `resolveMaxBudgetUsd()`. **Billing-aware**: the dollar cap is passed to the SDK as `maxBudgetUsd` only under API-key billing (`dollarCapped`); OAuth/subscription (Pro/Max) sessions are turn-limited instead (no dollar figure). A running-cost tripwire warns once at 80% (`DEFAULT_WARN_FRACTION`) — see Session Budget Guard.
- **Max turns**: 100 with a live session; 40 in bundle-only mode (`LIVE_MAX_TURNS` / `BUNDLE_MAX_TURNS` — bundle-only has no mutation/verify rounds)
- **Streaming**: `includePartialMessages: true` — text deltas stream to stderr in real-time
- **Session**: `persistSession: false` — no state between sessions
- **Client ID**: `env.CLAUDE_AGENT_SDK_CLIENT_APP = "admin-agent"` — identifies app in API headers

After `buildSystemPrompt()`, `runAgent()` runs `checkPromptBudget()` (see Prompt Budget Tripwire) to surface the assembled prompt's token cost.

The loop handles `SDKCompactBoundaryMessage` (logs pre-compaction token count), `SDKRateLimitEvent` (warns on throttling/rejection), `SDKSystemMessage` init (warns on MCP server connection failures), and `control_request` (logs mid-session re-authentication requests). Anthropic authentication is handled earlier by `auth/preflight.ts` in `main()`, before Kinetica credentials are collected. Session summary uses SDK-provided `duration_ms`, `duration_api_ms`, `total_cost_usd`, and `permission_denials`.

### Tool Architecture (`tools/`)

Each tool takes `KineticaSession` and returns `ToolResult<T>` — a discriminated union (`ok: true` with data, or `ok: false` with status/error/raw).

**Shared REST utility** (`tools/rest/parse-data-str.ts`): `parseDataStr<T>()` safely double-decodes Kinetica's `data_str` JSON responses. Returns a discriminated union (`ok: true` with parsed data, or `ok: false` with error details). Never throws. Used by most REST tool implementations.

**Type schema parser** (`tools/rest/parse-type-schema.ts`): `parseTypeSchema(schemaJson)` extracts column names and Kinetica-native types from the Avro-like `type_schemas` JSON returned by `/show/table` with `get_column_info`. Handles union types (`["type", "null"]`). Returns empty array on parse failure (never throws). Used by `show-table.ts`.

**Nested JSON decoder** (`tools/rest/decode-nested-json.ts`): `decodeNestedJsonStrings()` recursively decodes JSON-encoded string values in Kinetica responses. Handles triple-encoding (e.g., `statistics_map.ranks` → per-rank JSON strings → inner objects). Pure, never throws. Used by `metrics.ts` and `node.ts`.

**Rank stats flattener** (`tools/rest/flatten-rank-stats.ts`): `flattenRanksSummary()` and `flattenRankDetail()` convert decoded rank statistics into tabular rows. Safely handles missing `tier.stats` objects. Used by `metrics.ts` and `node.ts`.

**Host manager port discovery** (`tools/rest/discover-hm-port.ts`): `discoverHmPort(session)` reads `conf.hm_http_port` from system properties and falls back to `DEFAULT_HM_PORT` (9300). Never throws. Shared by `cluster.ts`, `host-manager.ts`, `show-configuration.ts`, and `alter-configuration.ts`.

**Shard summarizer** (`tools/rest/summarize-shards.ts`): `summarizeShards()` reduces the raw 16,384-entry shard array from `/admin/show/shards` into a compact per-rank distribution summary with a `balanced` flag. Without this, the shard map overwhelms the truncation budget. Used by `cluster.ts`.

**REST tools** (`tools/rest/`) — 14 tools calling Kinetica REST endpoints via `session.makeRequest()`:

| -------------------- | ------------------------------------------ | ------------------------------------------------------------------------------------------------ |

**SQL tools** (`tools/sql/`) — 2 tools + 1 error enricher:

- `explain` — wraps statement with EXPLAIN automatically
- `enrich-error` — enriches SQL errors with verified column names from discovered schemas

**Mutation tools** (`tools/mutation/`) — 4 tools requiring user approval before execution:

| Tool                      | Endpoint                                    | Notes                                                                                         |
| ------------------------- | ------------------------------------------- | --------------------------------------------------------------------------------------------- |
| `alter-system-properties` | `/alter/system/properties`                  | Edits `gpudb.conf` in place (persists; restart may be needed); returns a `verification` state |

| `alter-configuration`     | `/admin/alter/configuration` (HM port 9300) | Replace full gpudb.conf with before/after verification                                        |

Mutation tools are annotated `{ destructiveHint: true, readOnlyHint: false }` — not in the diagnostic allow-list, so they trigger the `canUseTool` approval gate. Each mutation logs an audit line to stderr (EXECUTED/FAILED + input summary) via `logMutationAudit()`.

**Batch column tool** (`tools/mutation/alter-table-columns.ts`): `kinetica_alter_table_columns` batches 2+ column type/property changes on a single table into one efficient ALTER TABLE statement. Registered read-only in `buildApprovalRegistry()` (so the gate does not prompt) because it implements its own two-step approval: interactive checkbox for column selection + SQL preview with y/n confirmation. Uses `showChecklist()` from `approval/checklist.ts` for the checkbox UI and `executeMutationSql()` for execution.

**Report tool** (`report/save-report.ts`): saves timestamped markdown (`kinetica-diag-YYYY-MM-DD-HHmmss.md`) to `reports/` with credential scrubbing. Supports `partial` flag for interrupted investigations. Annotated `readOnlyHint: true` and registered read-only in `buildApprovalRegistry()`, so the approval gate does not prompt — the consent check below is the real gate, and prompting in both places would ask the operator twice for one save.

**Save consent is a Y/n widget raised mid-turn, and a TOKEN the handler takes** (`report/confirm-save-report.ts` + `report/save-consent.ts` + `cli/confirm-save.ts`). `confirm_save_report` takes **no arguments**, shows the operator `Save this report to disk? (Y/n)` via the themed `confirm()` prompt, and returns their answer as a tool result — so the agent keeps its turn and the operator types nothing. The answer is recorded in a shared one-shot `SaveConsent` (`granted | denied | unasked`) that `save_report` consumes before writing: no grant, no file.

It was **conversational** until 2026-09-16 — both prompts told the agent to ask "save this report? (yes/no)", end its turn, and wait for free text. That cost a whole turn plus a SECOND composition of the entire report (once as the turn text the operator reads, again as the tool argument after the yes), and it made consent only as strong as the model's obedience to a prompt sentence — the same coupling that dropped `## Timeline` when the `sonnet` alias moved. The old rationale for _not_ confirming inside `save_report` was correct and is preserved by the design: that handler receives the whole report as an argument, so asking there would leave the operator watching a spinner through an entire silent composition first. Asking from a **content-free** tool lands the question at the same moment the prose version did. Three deliberate bypasses: `partial: true` checkpoints under budget pressure (which must also NOT consume a pending grant — it belongs to the final report), a non-interactive terminal (assumes yes with a stderr note, so CI and evals produce artifacts rather than hanging on a prompt nobody can answer), and an aborted prompt (declines). A `denied` state is final — the handler never re-prompts, since re-asking an operator who just said no is how a confirmation becomes a reflex; an `unasked` state (the model skipped the ask tool) falls back to prompting inline rather than failing, because failing would make the model re-emit the whole report to retry.

The barrel `tools/index.ts` wraps each tool with the SDK's `tool()` helper and applies the output pipeline: `formatOutput()` → `truncateOutput()`. Exports `DIAGNOSTIC_TOOL_NAMES` (16-element `as const` tuple), `makeDiagnosticTools()` (16 MCP tool objects), `MUTATION_TOOL_NAMES` (4-element `as const` tuple), `makeMutationTools()` (4 MCP tool objects), `ALTER_TABLE_COLUMNS_TOOL_NAME`, and `makeAlterTableColumnsToolWithDeps()`. The save_report and confirm_save_report tools are created separately via `makeSaveReportTool(deps)` and `makeConfirmSaveReportTool(deps)`, both taking the shared `SaveConsent` and the operator prompt.

### Types (`types/index.ts`)

Centralized type contracts: `Credentials`, `KineticaSession`, `ApprovalResponse`, `ToolAnnotation`, `TruncationOptions`, `ToolResult<T>` (discriminated union with `ToolSuccess<T>` / `ToolFailure`), `Playbook` (title, category, severity, keywords, body, filename), `Reference` (title, category, keywords, body, filename — no severity). All properties are `readonly`. Exports `DEFAULT_TRUNCATION` constant (head 150 + tail 50 lines). Additional types in their respective modules: `CollectResult` (credentials + prompted fields set) in `session/collect.ts`, `ResolveUrlResult` (discriminated union) in `session/resolve-url.ts`, `LogoutResult` in `auth/logout.ts`.

`KineticaSession` exposes `makeRequest(endpoint, body?)` for the default Kinetica port and an optional `makeRequestToPort(port, endpoint, body?)` for cross-port requests (e.g., host manager on 9300).

### Output Pipeline (`output/`)

Tool results flow through: raw data → `reshape.ts` (objects → row arrays) → `format.ts` (JSON → markdown tables/key-value pairs) → `truncate.ts` (head 150 + tail 50 lines). Agent text output goes through `streaming-table-aligner.ts` (line-buffered adapter that detects markdown table blocks in streamed deltas, reformats with aligned columns via `reformat-tables.ts`, and passes non-table content through immediately). `render-markdown.ts` handles terminal rendering of markdown content. `format-tool-name.ts` strips `mcp__<server>__kinetica_` prefixes for human-readable tool names in logs and audit output. `spinner.ts` provides a braille-dot terminal spinner (`createSpinner()` factory) that animates on stderr during agent thinking and tool execution gaps — auto-suppressed in non-interactive terminals and test environments.

### Schema Discovery (`agent/discover-schemas.ts`)

At startup, queries `ki_catalog.ki_columns` to discover actual column names for 18 system tables. Results feed into `diagnostic-sql.ts` builder functions that generate version-correct SQL examples for the system prompt. Falls back to hardcoded SQL when discovery fails (graceful degradation — never throws). Skipped in both degraded and bundle modes (needs the live DB engine).

### Offline Bundle Mode (`bundle/` + `tools/bundle/`)

Lets the agent diagnose from an extracted `gpudb_sysinfo` support bundle. A bundle and a live connection are **composable capabilities**, not exclusive modes — a session can hold either or both, so the agent can correlate frozen bundle evidence (what happened) against current live state (what's true now). The reasoning layer (playbooks, references, report template) is reused wholesale.

**`bundle/` (the data source — analogue of `session/`):** pure parsers + a `BundleSource` facade. Each module is co-located with tests. Behavioral tests build **synthetic** fixtures at runtime (`mkdtemp` + `writeFile`) — no real bundle is ever committed (extracted bundles are gitignored; they carry license keys, LDAP binds, TLS material). The one exception is `real-bundle-coverage.test.ts`, a classifier coverage guard that embeds the relative **paths** (never contents) of real bundles as frozen golden snapshots — paths anchor the classifier to real collector layouts in a way synthetic data can't, while carrying no secrets. It now pins **two** layouts: a canonical 77-file `gpudb_sysinfo` bundle, and a 42-file **off-shape, logs-only** bundle (flat directory, rolling logs without the `core-` prefix, host-manager `.out` stdout, no config/version/os-diag) — the latter exercises the inference tiers. **Invariant: paths only, never file bodies.** To refresh/extend for a newer or divergent collector layout, add a snapshot (don't mutate in place); see the procedure in that file's header.

- **`parse-log-line.ts`** — tolerant parser for one Kinetica log line. Handles the core dialect (`TS SEV (pid,tid,r0/ctx) host source:line - msg`), the component dialect (no `source:line`/`-`), and the Loki/promtail JSONL dialect (`logs/rank*.log`) — the latter unwrapped to a standard line first via `unwrap-loki-jsonl.ts` (below). Severities `INFO/WARN/UERR/ERROR/FATAL`. Unparseable lines return `{ message: raw }` (never dropped). `severityRank()` orders severities for `minSeverity` filtering. Timestamps stay as fixed-width strings — lexical comparison is chronological, dodging timezone ambiguity — **within one clock**: every parsed stamp carries a `timestampZone`, mapped from the unwrapper's `stampSource` (`local` for Kinetica's own host-local stamp, which has no zone marker, and for a pass-through record that kept it; `utc` where a Loki export substituted its own). The bundle records no UTC offset, so the same event sits at two wall-clock times across the two log families, and lexical order across them is meaningless — the zone is surfaced so callers never order across it. The union is **bundle-scoped by design** (its doc says so): the live tools each render one fixed zone and declare it in their own note, so generalizing would mean a shared evidence clock in `types/index.ts` plus a field on `ToolSuccess`, not a wider union here.
- **`unwrap-loki-jsonl.ts`** — `unwrapLokiJsonl(line)` turns one Loki/promtail JSONL record (`{"line":"<loki-ts> <level> <job> <app> : <body>", …}`, exported under `logs/`) back into a standard `<ts> <body>` Kinetica line — the body keeps the original UPPERCASE severity. The `<ts>` is the record's RFC 3339 UTC `timestamp` field (trailing `Z`, so UTC by format) normalized to the core dialect's millisecond width, falling back to Loki's rendered stamp when the field is absent. It returns `{ line, stampSource }`, **not** a bare string: the three branches disagree about whose clock wrote the stamp (`utc-field` and `rendered` are Loki's, `passthrough` hands back the record's inner text with Kinetica's ORIGINAL host-local stamp), and only this function knows which ran. Inferring the zone from "did the unwrapper fire" labelled a pass-through local stamp `utc`, which suppressed the mixed-clock warning in exactly the case it exists for. Returns `undefined` for non-JSONL input (raw logs pass through). Called by `parseLogLine`, so search/timeline treat both formats uniformly. Without it a JSONL line starts with `{`, fails the prefix regex, and yields no severity — silently dropping every `minSeverity`-filtered rank-log line. Pure, never throws.
- **`sysinfo-block.ts`** — `parseSysinfo()` splits the universal `EXEC_CMD:`/`EXEC_END with exit code N` wrapper (used by every `.txt` artifact) into `{ command, output, exitCode? }` blocks; strips the path header and `### Showing whole log file` marker.
- **`classify-file.ts`** — maps a bundle-relative path to a `BundleFileKind` (`core-log | component-log | loki-tail | config | os-diag | process-info | version-info | collection-errors | manifest | unknown`) plus a **`confidence`** (`exact | inferred | weak`), a `reason`, and rank / service / host / component hints. Classification is an ordered **matcher table** in tiers: **Tier A** = canonical `gpudb_sysinfo` names/locations (→ `exact`); **Tier B** = generalized off-shape heuristics for bundles that don't match the known shape (→ `inferred`) — e.g. a rolling log shipped WITHOUT the canonical `core-` prefix (`gpudb-rolling-r3.log`), host-manager `.out`/service logs, any gpudb-prefixed log in a flat layout, and a log-ish file in a `logs`-named dir or carrying a rank token; **Tier C** = extension-only fallback (`.txt` → os-diag, log-ish → component-log, else `unknown`; → `weak`). The host manager (`hm`) is a singleton **service** (port 9300), NOT a rank, so it is tagged `service: "host-manager"` — keeping the `rank` vocabulary numeric so per-line rank filters and the inventory `ranks` list never see a service name. Component names have all trailing log-ish suffixes stripped (`.log`/`.out`/`.err`, incl. doubled `stats-loki-node2.log.log`). Loki per-rank exports (`logs/rank0.log` …) tag the numeric `rank`, `logs/hostmanager.log` the service; rotated logs (`…rolling-r0.log.1`) stay `core-log`. **Pure on the path, and the bundle-root folder name never affects the result** — the index walk strips it and the off-shape rules key off the BASENAME, so the bundle directory can be named anything (a host id, a ticket number, a random string). A rank from a loose name-token guess (vs. a canonical/rolling/content match) is flagged `inferredRank`, so the inventory can keep it out of the trusted rank count.
- **`sniff-file.ts`** — `sniffFile(absPath)`, the content-based fallback the index runs ONLY on `weak`-confidence files (skipping weak `os-diag`, which the `.txt` extension already placed — avoids ~20 discarded reads on a normal bundle). Reads a **bounded head** (≤8 KB, first ~20 non-blank lines — logs can open with a non-log preamble like host-manager `.out`'s `CPU ARCH:` banner, so it scans the window, not just line 1) and test-drives the existing parsers in order: `unwrapLokiJsonl` → `parseLogLine` (recovering the rank from the `(pid,tid,rN/…)` context — a content-derived rank, authoritative) → the shared `EXEC_CMD_RE` (sysinfo) → `parseIni` + the shared `SECTION_RE` (config). This is the "apply our parsers" half of off-shape support; `parse-ini.ts` and `sysinfo-block.ts` export `SECTION_RE`/`EXEC_CMD_RE` so the sniffer keys off the SAME grammar rather than re-declaring it. Returns `undefined` when nothing matches; pure aside from the bounded read, never throws.
- **`known-files.ts`** — `describeBundleFile({ relPath, kind })` returns a one-line description of what a canonical bundle file contains (distilled from the `gpudb_sysinfo.sh` collector's `run_cmd "<file>" "<command>"` mapping), so orientation tools (`kinetica_bundle_list_files`) can tell the agent WHAT a file holds without reading it. Matches by basename first, then falls back to a per-`BundleFileKind` description, then `""` (graceful — never wrong, just absent). Pure, never throws.
- **`parse-ini.ts`** — `parseIni()` / `filterIni()` for gpudb.conf; surfaces `${…}` interpolation references verbatim.
- **`log-search.ts`** — streaming search (`searchLogFile`) and timeline aggregation (`aggregateTimeline`) via `node:readline`. **Never reads a log whole** — results are bounded (the true total is still reported) and timeline buckets collapse millions of lines into per-time-bucket severity counts. This is the core defense against context blowup (a real rank log is ~20 MB / 100k lines). Both results carry `zones` — the clocks (`local`/`utc`) among the matched or counted lines, in stable order — so a caller can tell when one result spans both log families. Accumulation is a **bitmask** (`ZONE_BITS`/`ALL_ZONE_BITS`, rendered by `orderZones(mask)`), not a `Set`: the accumulator runs on every MATCHED line — a filter-less search matches all ~140k of them — and a `Set` measured ~2 ms slower per 20 MB log, while the mask also allows an early-out once both bits are set. Same per-line-work discipline as `unwrap-loki-jsonl.ts`'s fast reject. Opt-in **multi-line coalescing** (`coalesceMultiline`, surfaced as the tool's `include_multiline`): a Kinetica log record can span several physical lines when a logged value contains embedded newlines — most often the SQL on an `Executing SQL:` line. Because continuation lines carry no timestamp prefix (a new record always starts with one), a line-oriented match returns only the first line and the agent sees a truncated query. With coalescing on, each returned match absorbs the timestamp-less lines that follow it up to the next record, bounded by `MULTILINE_MAX_LINES`/`MULTILINE_MAX_CHARS` (the reconstructed text lands in `message`; `raw` stays the first line; the record is still counted once, and continuations are not re-tested as independent matches). This only recovers the full statement from the **rolling core logs** (`logs-local/`), which preserve the SQL's embedded newlines; the **Loki per-rank tails** (`logs/rankN.log`) frame each physical line as its own JSONL record, so promtail keeps only the statement's first line and there are no continuation lines to stitch there — `selectLogFiles` prefers the rolling log per rank, so the workflow lands on the right file whenever a rank has one.
- **`bundle-index.ts`** — `buildIndex()` recursively scans the directory into classified `FileIndexEntry[]` (path, kind, `confidence`, `reason`, rank, `inferredRank`, service, host, size). Bundle-root confinement is **two layers**, both enforced before any byte is read: (1) a leaf `lstat` symlink/isFile guard (drops a file that is itself a symlink), and (2) a `realpath` check that drops any entry whose resolved real path escapes the bundle root — defeating a **symlinked parent directory** (`readdir(recursive)` descends through it and yields real files inside the target, which a leaf-only check would index; e.g. `logs-local → $HOME` leaking `~/.ssh/id_rsa`). Because the index is the single chokepoint every read sink draws from, this one check confines all of them (`searchLogs`, `readConfig`, `sniffFile`, …). After classification, `refineWithContent()` upgrades a `weak` entry via `sniffFile` when content adds information (a different kind, or a rank/service the name lacked); a content-derived rank replaces the path one WITHOUT the `inferredRank` flag (it's authoritative).
- **`BundleSource.ts`** — `createBundleSource(dir)` facade: `listFiles`, `detectVersion` (gpudb.txt → gpudb.conf `file_version`), `readConfig`, `readSysinfo`, `searchLogs`, `logTimeline`, `collectionErrors`, and `resolve` (confines all reads to the bundle root — rejects `..` escapes). Log file selection is by numeric `rank`, `hostManager` (the host-manager log), or `component` — all **FILE** selectors, resolved once at the file level and NOT re-applied per line (the per-line streaming searcher receives only the line filters), so a rank/host-manager-scoped query never drops continuation/stack-trace lines that carry no rank token. `selectLogFiles` applies **per-rank precedence**: a rank's rolling core log (`logs-local/`, full history) supersedes its Loki tail (`logs/rankN.log`), but ranks present only as tails (workers on other hosts) are still selected — so a cluster-wide search covers every rank, not just the collector host's. `hostManager` likewise prefers the rolling hm log and falls back to `logs/hostmanager.log`; `component` matches both `component-log` and the Loki component tails under `logs/`. `searchLogs` scans **every** selected file to report an accurate cross-file `totalMatched` (only the returned match payloads are capped, so `capped` is honest); `searchLogs` and `logTimeline` both merge the per-file `zones`, so a cluster-wide result that mixes a rolling log with a Loki-only rank's tail reports both clocks; `inventory()` reports numeric `ranks` and non-rank `services` (e.g. `host-manager`) separately, plus `inferredRanks` (loose name-guess ranks, kept out of the trusted `ranks`), `inferredFiles`, and `unknownFiles` counts. `assessLayout(inventory)` (exported here, **shared** by `verify-bundle` and the list-files tool) returns a `layout` verdict (`canonical | partial | unfamiliar`) + a non-canonical `layoutWarning`, anchored on the presence of `config` + `version-info` (the artifacts a bare logs dump never has — deliberately NOT `os-diag`, whose only source is the weak `.txt` fallback) and the inferred-file fraction.
- **`verify-bundle.ts`** — `verifyBundle(path)`, the `connectWithRetry` analogue: validates the path (fails fast on a `.tgz` with an extract-first message), builds the source, and returns version + inventory + `missingExpected` + `layout`/`layoutWarning` (all non-fatal, mirroring degraded mode's never-hard-fail philosophy) — the CLI warns the operator on stderr when the bundle is off-shape (`partial`/`unfamiliar`).
- **`bundle-holder.ts`** — `createBundleHolder(initial?)`, a lazy `BundleSource` ref. Because the SDK fixes the tool set at `query()` creation, bundle tools bind to this holder (not a `BundleSource` directly) so a live session can attach a bundle mid-conversation; `kinetica_load_bundle` populates it.

**`tools/bundle/` (6 file-backed tools):** `kinetica_load_bundle` (attaches a bundle into the holder — for the "analyze a support bundle" request mid-session; called **without a path**, it triggers an interactive directory picker via `cli/pick-bundle-path.ts` `promptBundleDirectory()` — a `search`-based autocomplete injected as `makeBundleTools(holder, { promptForPath, confirmPath })` — so the operator selects the directory instead of typing it; if the **model** supplies an explicit `path` instead, `confirmPath` requires the operator to approve that exact path first, since loading widens the agent's file-read surface to that directory — a picker-chosen path is already operator consent and skips the second prompt), `kinetica_bundle_list_files` (orientation — also surfaces `layout_match`, a `layout_note`, per-file `confidence`/`why`, `inferred_ranks_unconfirmed`, and capped `unknown_file_paths` for off-shape bundles), `kinetica_bundle_log_timeline` (incident shape — call before search), `kinetica_bundle_search_logs` (supports `include_multiline` to stitch a multi-line record — e.g. the full `Executing SQL:` query — back onto each match; both log tools report `timestamp_zone` and, when one result spans both clocks, append the mixed-clock warning from `tools/bundle/timestamp-zone.ts` — search adds a per-row `zone` column only then, timeline warns that its buckets merge two clocks and says to isolate one family with `rank=`/`host_manager=`), `kinetica_bundle_read_config`, `kinetica_bundle_read_sysinfo`. Each returns `ToolResult<T>` through the same `applyOutputPipeline` as the live tools; data tools return a polite "no bundle loaded" failure until one is attached. `catalog.ts` is a **separate** `Record<BundleToolName, ToolCatalogEntry>` typecheck guard (bundle tools never leak into the live `ToolName` union). `index.ts` exports `BUNDLE_TOOL_NAMES`, `makeBundleTools(holder)`, and `createBundleRegistry()`.

**Live cross-check:** `session/verify.ts` `connectBestEffort()` makes a non-interactive, env-only live connection (no prompts, no exit, returns `undefined` if unreachable) so bundle analysis can verify against the live system when possible.

**Prompt:** `agent/observability-section.ts` `buildObservabilitySection(client, context)` is shared by BOTH prompt builders and gates every claim on the endpoint backing it — a Loki-only stack is never told `kinetica_tier_snapshot` is the first move for memory pressure, since it would call it, get "not configured", and burn a turn. The bundle-only prompt gets it too, with its own framing: the stats stack is on a different host and commonly outlives the cluster the bundle came from.

**Bundle prompt + wiring:** `agent/bundle-system-prompt.ts` `buildBundleSystemPrompt()` is the **bundle-only** prompt (no live connection — read-only, 3-round diagnose→report, no mutation rounds). When a live session exists, `buildSystemPrompt()` is used instead with a `bundleCapability` arg (`"attached"` | `"available"`) that injects a **Support Bundle Capability** section teaching the correlate-history-vs-now workflow. Both reuse the playbook/reference formatters in `agent/prompt-sections.ts`. `agent/run-agent.ts` takes an optional `session` **and** `RunAgentOptions.bundleSource`, seeds a `bundleHolder`, and assembles the **union**: live tools (diagnostic + mutation + alter — only when a session exists) + bundle tools (always, via the holder) + confirm_save_report + save_report; `allowedTools` and the read-only registry are the corresponding union; `maxTurns` is 100 with a live session, 40 bundle-only. Schema discovery is skipped without a live session. The streaming loop and budget guard are capability-agnostic and unchanged.

### Observability (`observability/` + `tools/observability/`)

Read-only access to a cluster's Prometheus / Loki stats stack. Composable with everything else — a session may have a live connection, a bundle, an observability stack, or any combination. Design decisions here are grounded in measurements taken against a live 7.2.3.20 kagent-installed cluster; the traps below are the load-bearing ones.

**`observability/` (the data source — analogue of `session/`):**

- **`ObservabilityClient.ts`** — `createObservabilityClient(endpoints, opts?)`. GET-only, and deliberately NOT built on `KineticaSession`: that session POSTs with a `Basic` header from closure-captured DB credentials, and reusing it would send those credentials to third-party services on every query. This client passes **no headers at all**, which its test asserts for every method. Prometheus bounds are typed `number` (second epochs) and Loki bounds `string` (nanosecond epochs, which exceed `Number.MAX_SAFE_INTEGER`), so swapping them is a typecheck error rather than a silent wrong-window query. Methods: `promInstant`, `promRange`, `promRules`, `promAlerts`, `promConfig`, `lokiRange`, `lokiLabels`. (`promRules` backs `kinetica_prom_alerts`. `promAlerts` is exposed and tested but deliberately **unwired**: `/api/v1/alerts` is only the flattening of the `alerts[]` arrays `/api/v1/rules` already embeds per rule, so reading it would be a second round-trip for data the first call returned — and structural nesting makes rule-to-instance correlation exact, with no join key and no chance of a stale pairing. `promConfig` is exposed and tested but unwired; its value is rank topology from `scrape_configs` while the DB is down, which is a different tool.)
- **`tools/observability/response-body.ts`** — `readPromBody(response)` / `readLokiBody(response)` + `promError(body)`: the shared decode step **all four** stats-stack tools use, returning a body or a `ToolFailure` (never throwing), kept OUT of the client so `ObservabilityClient` stays transport-only. This is the stats-stack analogue of `tools/rest/parse-data-str.ts`. It exists because **Prometheus answers a malformed query with HTTP 200 and `{"status":"error","error":"…"}`**, so a tool checking only `response.ok` reports a rejected query as a successful empty result. That is not hypothetical: `tier-snapshot.ts` carried a drifted copy that checked only `response.ok`, so a rejected query fell through to `summarizeSeries`, found no series, and reported the reassuring "No ki_db_tier series returned" — a rejected query read as "this cluster has no tier metrics". Consolidating the four copies fixed it, and a test now pins it. The two services differ in exactly two declared ways: Loki appends a LogQL hint to its HTTP-failure message, and has **no** body-level error check, because no 200-level JSON error envelope is known for it here (its failures arrive as a non-200, commonly with a plain-text body the non-JSON branch already reports) — applying Prometheus' check there would invent behaviour rather than encode measured behaviour.
- **`discover.ts`** — `discoverObservability(opts)` returns `{ endpoints, unreachable }`. Never throws. **Loki is DECLARED in `gpudb.conf`; Prometheus is not, anywhere** — structural, not an oversight: the database pushes events to Loki and alerts to Alertmanager so it must hold their addresses, while Prometheus pulls by scraping the ranks, and a scrape target never needs its scraper's address. So Prometheus is found by probing `:9090` on the event-server host and that inference is verified, never assumed. `unreachable` lists only DECLARED misses, so "deployed but unroutable" (which has a fix) stays distinguishable from "not deployed" (which does not). Host resolution order, **every entry identity-probed** (nothing is trusted blind, so a typo surfaces at startup rather than on every tool call): `KINETICA_STATS_HOST` → `gaia.event_server_public_address` → `gaia.event_server_address` → that address's declared `hostN.public_address` translation → the database host the operator reached. Ports are per SERVICE, never per host — Prometheus 9090, Loki `gaia.event_server_port` (default 9080). **One host variable, not two URLs**, because that is the model `gpudb.conf` itself uses (one address, several ports), Prometheus's runtime config scrapes Loki at `localhost`, and kagent installs the stack as a unit under one directory: two URLs would invent a split the product cannot produce. **Probes verify service IDENTITY, not just liveness** — `/api/v1/status/buildinfo` must return a version for Prometheus, `/loki/api/v1/labels` must return `status: "success"` for Loki. "Something answered on this port" is not evidence: on RHEL/CentOS, Cockpit owns **9090** by default, including on the database host the fallback tier probes, so a liveness-only check would report `Observability: Prometheus` on a cluster that has none. (Loki's `data` is optional there — that endpoint defaults to a 6-hour window and a quiet cluster answers a bare `{"status":"success"}`; requiring the array rejected a healthy Loki in live testing.) **Alertmanager is deliberately not discovered**: no tool reads it (its rules and firing state are both readable through Prometheus), and probing it added ~3s to _every_ startup — an env override for Prometheus/Loki does not cover it, so it timed out against the internal address on each launch. Measured: removing it took a configured startup from 3,066 ms to 84 ms.
- **`cli/observability-setup.ts`** — `setupObservability({ session?, bundleSource? })` owns the question discovery cannot answer for itself: where the property map comes from. A live session reads `/show/system/properties` (`conf.`-prefixed, and it **omits** `event_server_port`/`alertmanager_port`, so the defaults carry them); a bundle-only session reads the bundle's captured `gpudb.conf` (bare keys, ports included). Returns the client plus one dim startup line. Never blocks startup.

- **The stats host is COLLECTED, not derived.** `session/collect.ts` asks "Prometheus/Loki host URL (e.g. http://statshost, blank if none):" immediately after the password, and it rides along with the other connection details: `Credentials.statsHost` → `ConnectResult.statsHost` → `RunAgentOptions`/`setupObservability`. It is saved to `.env` by the existing `offerSaveCredentials()` (via `upsertEnvValue()`, a focused pure helper kept separate from `buildEnvContent()`, which owns the URL/USER template). Rationale: `gaia.event_server_address` names the cluster's INTERNAL address, which usually does not route from wherever the agent runs, so deriving it first would mostly produce something unreachable and a second prompt afterwards. Config remains the silent fallback when the answer is blank — still correct for an agent running on the cluster network. The question is skipped on the "Use saved connection? (Y)" path, whose whole contract is to ask nothing: a blank answer cannot be remembered (`loadEnvFile` skips empty values so prompts still fire), so asking there would nag every launch of a cluster with no stats stack. Non-interactive terminals never prompt.

**`tools/observability/` (4 tools):** `kinetica_prom_alerts` (the site's OWN alert thresholds plus what is firing now — the Round-1 orientation move), `kinetica_tier_snapshot` (per-rank/per-tier utilization with an eviction verdict — the first move for any pressure question), `kinetica_prom_query` (arbitrary PromQL, summarized), `kinetica_loki_query` (structured event streams, plus promtail-shipped rank log lines via `stream="logs"`). `catalog.ts` is a **separate** `Record<ObservabilityToolName, ToolCatalogEntry>` typecheck guard, mirroring `tools/bundle/catalog.ts`, so these never leak into the live `ToolName` union. Adding a tool means touching only `OBSERVABILITY_TOOL_NAMES` plus that catalog and `TOOL_ENDPOINT` — the read-only registry derives from the tuple, and **both remaining spots are full `Record`s over `ObservabilityToolName`, so an omission is a typecheck error rather than a silent gap.** `TOOL_ENDPOINT` (in `tools/observability/index.ts`, beside the tuple and the factories) is the **single declaration of which endpoint each tool needs**, and both consumers derive from it: `withClient()` gates the tool on the matching `promUrl`/`lokiUrl`, and `buildObservabilitySection()` decides whether to ADVERTISE it in the prompt. It was briefly declared twice — a `"prom"`/`"loki"` map in `agent/observability-section.ts` for the prompt, and separate `"promUrl"`/`"Prometheus"` literals at each `withClient()` call — which typechecks even when the two disagree, so a tool could be advertised on the one stack where it does not work and suppressed on the stack where it does. Before that it was two hand-maintained arrays (`PROM_TOOLS`/`LOKI_TOOLS`), where a missing tool stayed registered but vanished from the prompt's evidence checklist entirely. Registered **unconditionally** (the SDK fixes the tool set at `query()` creation), returning a failure that names the env-var fix when no endpoint was found. Available in bundle-only sessions too, on purpose: the stats stack runs on a different host and commonly outlives the cluster the bundle came from.

**Metric semantics that will bite you** (encoded in `tier-snapshot.ts`, restated in the prompt):

- Rank identity is the **`source`** label (`rank0`, `rank1`, …). There is no `rank` label.
- `ki_db_tier{what="size_bytes"}` is the tier **LIMIT**, not the current size. `-1` means uncapped, so no percentage is meaningful (measured on `disk0` and `persist`).
- `high_watermark` / `low_watermark` are **fractions** of the limit (0.9 / 0.8), not byte counts. Eviction begins at `high_watermark × size_bytes`, so real headroom is the distance to that trigger, not `limit - used`.
- `evictions_total` is cumulative since process start — non-zero means it HAS evicted, not that it is evicting now.
- Rank 0 reports only `size_bytes` and `used_bytes` (no watermarks, no eviction counters) because the head node holds no data tiers.
- Byte values are formatted **base-1000**, matching how tier limits are configured; base-1024 silently overstates headroom.
- An **instant** query returns `resultType: "vector"` with a singular `value`; a range returns `matrix` with plural `values`. `summarizeSeries()` normalizes both — reading only `values` silently summarizes every instant query to zero series.
- A **nonexistent metric returns HTTP 200 with an empty result**, identical to a metric with no data in the window. Both tools say so rather than reporting "no data".
- Loki holds **two populations**, selected by `lokiQuery`'s `stream` argument, sharing only the `cluster`/`host`/`ring` labels:
  - **events** (always) — pushed by the database, keyed by `class`: `sql` (per-statement jobid/user/resource_group/elapsed/statement), `job`, `status`, `config`, `mode`. Bodies are JSON, and Kinetica does **not escape quotes inside the `{"log":"…"}` envelope**, so `JSON.parse` fails on precisely the error messages worth reading — `renderEntry()` falls back to a lenient extractor. Multi-line SQL statements are collapsed to one line because a raw newline terminates a markdown table row.
  - **log lines** (only with `enable_promtail=true`) — shipped by promtail, keyed by `job` (`gpudb_log`, `gpudb_sql_log`, `gpudb_graph_log`, `gpudb_reveal_log`, `gpudb_tomcat_log`, `gpudb_tomcat_access_log`, `gpudb_workbench_log`, plus the stats stack's own logs) with `app`, `level` and `filename`. Bodies are **plain-text core-dialect lines**, so `renderEntry()` hands them to `bundle/parse-log-line.ts` — the same parser the bundle tools use — which strips ~90 chars of timestamp/pid boilerplate already carried as columns (this is why `MAX_MESSAGE_CHARS` did not need raising for the logs path).
- **Events are telemetry, not logs — and nothing used to make the agent read the logs at all.** Measured on a live cluster: a full health check reported eleven dimensions OK, including "0 job-class error events in Loki", having never run a `stream="logs"` query. Three signals independently licensed the skip, and all three are fixed: the **evidence checklist** row for `kinetica_loki_query` described only the event stream, so rank log lines were not on the agent's map of available evidence at all (`OBSERVABILITY_TOOL_CATALOG` now names both populations and says to always read logs too); the **prompt** framed `stream="logs"` as available "ONLY when the cluster has `enable_promtail=true` (it is off by default)", which reads as probably-unavailable (now: always run it, the tool reports the verdict); and the **events result note** said "IF the cluster has promtail enabled, stream="logs" reaches the actual rank logs" — a condition that call cannot evaluate, so it read as permission to skip (now: "You have not read any rank log lines"). The general lesson: a capability described conditionally in the checklist is a capability the agent will not use, and an unevaluatable condition in a tool note is read as permission, not as a prompt to check.
- **Never infer promtail's state from an empty logs result.** Measured false negative on a live cluster: the agent ran a `severity="error"` logs query against a healthy cluster, got nothing, saw events present, and reported "promtail is not enabled" — while it was on and shipping ~60k lines/hour. The prompt had told it to make exactly that comparison ("events present and logs absent means promtail"), which is invalid the moment the logs query carries a filter. The `job` label is on every promtail stream and no event stream, so `/loki/api/v1/labels` is the one cheap fact that settles it: `lokiQuery` probes it on the empty-logs path only (the sole case where the answer changes what the emptiness means) and reports `shipping` / `absent` / `could not verify`, never a guess — an unanswered probe refuses both conclusions rather than defaulting to the alarming one. The prompt now forbids the inference and routes the config question to `kinetica_show_configuration`. A second trap compounded it: `severity` on **logs** is an EXACT `level` match, not the `>=` threshold the bundle tools give the same word, so `severity="error"` also excludes `fatal` and `uerr` — the note says so whenever that filter was in play.
- **`enable_promtail` is not live** — like every other `gpudb.conf` property it is written to the file and the running process never re-reads it. Measured: the setting sat enabled with **zero** log lines in Loki until the stats stack (`kinetica_stats`) was restarted, at which point lifetime ingest went from **282 lines to ~60k/hour**.
- **The two populations name the same things differently**, and mixing them up returns zero rows with HTTP 200. Severity is `severity` (`info`, `uerr`) for events but **`level`** (`info`, `warn`, `error`, `uerr`) for logs; the emitter is `source` (`rank0`, `hostmanager0`) for events but **`app`** for logs — where the same rank is spelled **`rank-0`** and the host manager drops its ordinal entirely (`hostmanager`, not `hostmanager0`). `toAppLabel()` and the per-kind matcher builder translate, so callers use ONE vocabulary (`source="rank0"`, `severity="error"`) whichever stream they read.
- **`stream` defaults to `events`, deliberately.** The base selectors are `{cluster=~".+",job=""}` for events, `{job=~".+"}` for logs, `{cluster=~".+"}` for all. The old default was `{cluster=~".+"}`, correct only while events were Loki's sole occupants: with promtail on, log lines outnumber events by orders of magnitude and `flatten()`'s sort-then-slice would spend the whole `limit` on them, silently burying the events. Supplying `job` flips the default to `logs`, since no event stream carries that label.
- **Events are defined by EXCLUDING promtail (`job=""`), not by requiring `class=~".+"`** — the two return the same rows here, but only the former is back-compatible _by construction_: on a cluster that never ran promtail nothing carries `job`, so the events base collapses to the pre-promtail `{cluster=~".+"}` byte for byte, with no dependence on a label schema measured against one install. A `class=~".+"` base would silently drop any event stream lacking that label and would hide a future third population entirely. Measured over full retention: 58 event + 28 promtail = 86 streams, `{cluster=~".+",job=""}` returns exactly the 58, and **zero** streams carry neither label. (LogQL needs one non-empty-compatible matcher per selector; `cluster=~".+"` supplies it, so the empty `job=""` matcher is legal — a bare `{class="",job=""}` is a parse error.)
- **Promtail BACKFILLS on start; events do not.** Events are pushed live, so Loki holds them only from when the database began emitting. Promtail tails the rolling logs from the beginning, so on start it ships whatever history those files still hold — measured, ~40 hours of log lines appeared the moment it started, with the earliest log line PREDATING the earliest event. So an empty logs window is not evidence that promtail was off during it, and enabling promtail mid-incident recovers the on-disk history rather than starting from zero. (This also explains the timestamp split below: during backfill, parent lines carry their parsed log time while continuation lines carry ingest time — hours apart.)
- **Prometheus alerting rules EMBED their live instances**, so `kinetica_prom_alerts` needs exactly one call. Each `alerting` rule in `/api/v1/rules` carries its own `alerts[]` (with `state`, `labels`, `value`, `activeAt`) beside the `query` that defines the threshold, so joining "what is firing" to "what does this site consider too high" is structural — no join key, and a rule edited since an alert fired cannot produce a mismatch. `/api/v1/alerts` is only those arrays flattened, which is why `promAlerts()` stays unwired.
- **Zero alerting rules is the ABSENCE of monitoring, not health — and it is NOT the kagent default.** Measured on a live 7.2.3.20 kagent install: Prometheus held **16 alerting rules**, loaded from a product-path rule file (`/opt/gpudb/kagent/stats/prometheus/alert_rules.yml`, named by Prometheus' own `rule_files`), covering host load average, memory, disk, concurrent requests and RabbitMQ HA queue depth. Their annotations are `_`-prefixed gadmin alert-builder metadata (`_metric`, `_target`), i.e. the stats UI manages them — which is why thresholds must be READ at runtime rather than imported into this corpus as prose, and is the whole justification for this tool. So an empty rule list on a kagent stack is itself a finding (rule file absent or failed to load), not the expected state; `promConfig`'s `rule_files` is the read path that would confirm it, which is a second reason that method is worth wiring. An earlier version of this file and of `noRulesNote`'s doc comment claimed zero was the likely default — the probe measurement contradicts it. Separately, Kinetica evaluates its own thresholds (`alert_memory_percentage`, `alert_disk_percentage`, heartbeat) and pushes them straight to **Alertmanager**, never to Prometheus — which is exactly why `gpudb.conf` declares `alertmanager_*` and never Prometheus at all (same structural reason discovery has to probe for it). So an empty Prometheus rule list says nothing about whether the database is alerting: those live behind `kinetica_cluster_status` (`/admin/show/alerts`). Both the tool's note and the prompt say so, because "no alerts firing" read as "nothing is wrong" is the single worst inference available here.
- **A rule whose `health` is `err` can never fire**, so without that column a broken rule is indistinguishable from a quiet one. It is reported as a monitoring gap. Health is treated as failing only when it is a _positive_ non-`ok` string — an absent field means this Prometheus does not report health, which is not evidence the rule is broken.
- **The rule set is CUSTOMER-MANAGED and changes freely after install** — sites edit, add and delete rules from the gadmin stats UI, so nothing below is an invariant. Treat every observation as one site at one moment, and never let the agent assert a rule-set property it has not just read. This is the whole reason the tool reads `expr` at runtime instead of the corpus carrying thresholds as prose; it is the same rule as the per-customer tier limits, for the same reason.
- **Observed once (kagent, Prometheus 3.5.5) — provenance, not expectation:** 16 alerting rules; `severity` authored **UPPERCASE** (`INFO`/`WARN`/`ERROR` — the case looks like a gadmin convention, the level set is not); no recording rules; annotations carrying gadmin builder metadata under `_aggregate`, `_comparison`, `_durationUnits`, `_durationValue`, `_entities`, `_metric`, `_target`, plus a human `subject`. Any of these can differ on the next cluster.
- **A rule's NAME can disagree with its `for`, so never infer dwell time from the name.** This is the durable lesson; the specific values are not. Observed on that install: names read `mem90for5m`/`disk95for5m` while `duration` was **0 on all 16 rules** — gadmin recorded the intent in `_durationValue`/`_durationUnits` annotations but emitted no Prometheus `for`, so those rules fired on a single scrape. Since customers edit rules freely, another site may well have a real `for`; what holds everywhere is that the name is an operator-typed label with nothing enforcing it. The tool reports `for` truthfully and the prompt tells the agent to cite that column, not the name.
- **A real `expr` is longer than one table cell, and the threshold is at the END.** Measured: the `mem*` rules are 214 chars ending `* 100 > 70`. `clampExpr` therefore elides the **middle** (keeping 40 tail chars), because head-only clipping — which is what it did until the live run — discarded every threshold while keeping the metric plumbing, i.e. it dropped the one thing the column exists to show.
- **Recording rules are counted but not listed.** A diagnostician wants thresholds, not derived-series definitions; the count still ships because an alert `expr` may reference one by name, which the agent can then read with `kinetica_prom_query`.
- Alert instances inherit the labels of the series that tripped them, so they carry the same redundancy `series-rows.ts` strips: `alertname` restates the rule name, and `job`/`instance` re-encode the rank `source` already names. Unlike `alertname`, those two **differ per rank**, so they escape common-label hoisting and would land on every row — `REDUNDANT_WHEN_SOURCE_PRESENT` lives in `tools/observability/label-rows.ts` with the other shared label primitives, so the rule cannot drift between the two tables.
- **Promtail is line-oriented, so multi-line records do not survive it.** A record whose value contains newlines (above all `Executing SQL:`) is split: the parent keeps its **parsed log timestamp**, while continuation lines land in a **separate stream with no `app` label** and **ingest-time** nanosecond timestamps. They therefore neither pair with their parent nor survive an `app`/`source` filter — measured, a 10-second window held 15 orphaned continuation lines and no parent at all. This is the same limitation `knowledge/references/bundle/support-bundle.md` documents for the bundle's Loki tails: complete multi-line SQL exists only in the rolling logs.

**Time-series reduction** (`tools/rest/summarize-timeseries.ts`): `summarizeSeries()` reduces a Prometheus response to per-series `{min, minAt, max, maxAt, first, last, delta, points}` — min and max carry **their timestamps**, because when a peak happened is usually the finding. Measured: one metric × 2 ranks × 60 steps is 3,472 bytes raw and 795 summarized (77% reduction). `tools/observability/series-rows.ts` renders these as table rows and **hoists labels shared by every series into a note** — repeating `cluster`/`ring`/`job`/`instance` per row measured ~150 characters of mostly-redundant text against a real cluster. Both renderers draw their label primitives from `tools/observability/label-rows.ts` (`renderNumber`, `renderPairs`, `commonLabelKeys`, `renderCommon`, `REDUNDANT_WHEN_SOURCE_PRESENT`) — a peer module rather than an export from whichever renderer needed them first, since the separator, the sort, the redundancy set and the number precision must read identically in both tables or the operator sees two vocabularies for one cluster. `tools/observability/alert-rows.ts` applies the same discipline to `/api/v1/rules`: dropping group/file/evaluation-timing metadata, templated `annotations`, and redundant labels, and clamping each `expr` to one table cell. **Live-measured** against a real kagent Prometheus 3.5.5 (16 alerting rules, none firing): 8,575 bytes → 5,427 (**37% reduction**). A payload modelled on the same shape predicted 40%, so the model was close. Read this as one site's snapshot, not an expected value: the rule set is customer-managed, and reduction tracks how much of _that_ site's payload is discardable. An earlier figure of 59% came from a synthetic 4-rule payload and **overstated the gain by ~19 points**, because everything that inflated it was material this renderer discards wholesale — Prometheus-idiomatic prose `annotations` (`summary`/`description`/`runbook_url`) and 3 recording rules. That is the general rule worth remembering: **reduction here scales with how much of the site's payload is discardable, not with rule count.** A gadmin-managed site has almost nothing to throw away (`_metric: "00001"` is 18 bytes) while its `expr` values are long and are deliberately KEPT, since they are the thresholds the tool exists to deliver — so 40% is the pessimistic, and more realistic, end.

### Knowledge Playbooks (`knowledge/playbooks/`)

Expert diagnostic runbooks loaded at startup by `agent/load-playbooks.ts`. Each playbook is a Markdown file with YAML frontmatter (title, category, severity, keywords) and a body containing symptoms, detection steps, root cause, and remediation.

Playbooks are **progressively disclosed** (see Progressive Disclosure below): the prompt carries one card per playbook — id, severity, and its Symptoms list, which is the natural retrieval trigger — and the body (Detection, Root Cause, Remediation) arrives through `kinetica_knowledge_read` when the symptoms match.

Current playbooks: `memory-pressure`, `gpu-out-of-memory`, `query-contention`, `resource-group-exhaustion`, `stale-rank`, `config-drift`. The loader resolves the playbooks directory relative to package root (works in both dev/tsx and bundled/CJS), returns empty array on any error (graceful degradation).

### Knowledge References (`knowledge/references/`)

Domain knowledge documents loaded at startup by `agent/load-references.ts`. Each reference is a Markdown file with YAML frontmatter (title, category, keywords, plus the disclosure fields `summary`, `read_when` and `disclosure`) and a body containing structured reference material. Unlike playbooks (which are diagnostic runbooks with severity), references are informational — they give the agent deep knowledge of Kinetica internals.

References are progressively disclosed too. `summary` (≤ 220 chars) and `read_when` (≤ 160 chars) are what the prompt's card renders, and both are **required** on every on-demand reference — `src/knowledge/corpus.test.ts` fails the build without them. `read_when` must be an unconditional, phase-anchored trigger ("Before writing ANY SQL you hand to the operator"), never a topical hint: a capability described conditionally is one the agent will not use. `disclosure: inline` opts a document out and back into the old always-present rendering; only `mutation-safety.md` sets it today, because it is policy the agent cannot know to go and look up.

Current references (11): `gpudb-conf` (master config file, section index, admin parameters, tiered storage semantics), `tiered-objects` (`ki_tiered_objects` schema + diagnostic queries), `catalog-enums` (enum decoders for `ki_catalog` integer columns), `catalog-joins` (safe join paths between `ki_catalog` tables, oid compatibility, naming caveats), `rank-architecture` (rank 0 vs worker ranks, head-node profile, shard ownership, query-log locality for crash forensics), `mutation-safety` (pre-execution checklist for rebalance, alter-config, and DDL — injected into the system prompt by the reference loader, replacing the previously inline Mutation Safety Rules block), `sql-alter-table` (7.2 ALTER TABLE grammar, column property flags, shard-key immutability), `sql-create-index` (column index vs chunk skip index), `sql-dialect` (PostgreSQL-baseline mental model + a "false friends" table of cross-dialect SQL that looks valid but fails in Kinetica — e.g. `TRY_CAST`/`SAFE_CAST`, backtick quoting, timestamp subtraction, `NUMERIC` vs `DECIMAL`; the antidote to remediation SQL imported from SQL Server/Snowflake/Oracle. Dialect facts adapted from the official `kineticadb/agent-skills` corpus), `service-management` (the ONLY sanctioned start/stop/restart commands — `systemctl` unit names for `gpudb`/`gpudb_host_manager`/`kinetica_stats`/`gpudb-mq` as root, the `/opt/gpudb/core/bin/gpudb <component>-<directive>` script as the `gpudb` user, full-stack start/stop ordering, plus a "never emit" table. Corrects two long-standing errors in this corpus: `gadmin` is the web GUI and NOT a service-control CLI, and Kinetica has **no per-rank restart** — ranks are Host-Manager-supervised, so a rank restart means restarting the database on that host), `version-quirks-7.2` (endpoint/property differences between 7.2.x and earlier releases). The loader reuses `parseFrontmatter()`, `extractBody()`, and `findPackageRoot()` from `load-playbooks.ts`.

Bundle-scoped references live in `knowledge/references/bundle/` and load via a **separate** path: `loadReferences()` reads the top-level dir and **excludes** `bundle/`, while `loadBundleReferences()` reads only `bundle/`. `loadBundleReferences()` runs in **every** session (live or bundle-only), because the bundle tools are always registered — a bundle can be attached mid-session via `kinetica_load_bundle` — and the system prompt is built once at `query()` creation. What reaches the prompt now depends on the capability: **inline** in bundle-only mode and when `bundleCapability === "attached"` (the bundle is the session's subject, every tool call depends on this knowledge, so deferring a certain read buys nothing), and a **card** when a bundle is merely `"available"` (2.6k tokens of parsing detail is dead weight for a session that never attaches one). The deferred read is not lost: `kinetica_load_bundle`'s own result note instructs it at the moment of attach, which is the more reliable channel — it arrives when the capability becomes real rather than as a startup rule the agent must remember. Currently one bundle reference: `support-bundle` (bundle layout, the two per-rank log families, raw + Loki-JSONL log-line formats, severity ordering, file parsing, crash-SQL forensics, and how to work an **off-shape bundle** — the `layout_match`/per-file `confidence` signals, `unknown_file_paths` to inspect by hand, and inferred-rank caveats).

### Progressive Disclosure (`src/knowledge/` + `tools/knowledge/`)

The knowledge corpus is **not** rendered into the system prompt in full. Each document reaches the model at one of two tiers, chosen by its frontmatter `disclosure`:

| Tier          | Where                 | Cost           | Contents                                                     |
| ------------- | --------------------- | -------------- | ------------------------------------------------------------ |
| **inline**    | system prompt, body   | every turn     | Policy the agent must obey **without knowing to look it up** |
| **on-demand** | system prompt, 1 card | ~60-90 tok/doc | id, what it covers, and the unconditional trigger to read it |
|               | tool result           | only when read | the full body, or one `##`/`###` section of it               |

Measured: the live `"available"` prompt fell **22,657 → 9,290 tokens (−59%)**, bundle-only **19,599 → 8,359 (−57%)**. The win is context headroom and instruction focus, not dollars — the SDK caches the system prompt, so corpus tokens were already ~0.1× per turn. What they cost was a fixed ~16k tax on every turn's context window, earlier compaction, and attention spread across material irrelevant to the investigation at hand.

- **`src/knowledge/normalize-doc.ts`** — `normalizeDoc()` resolves every derived field once (`id`, `kind`, `disclosure` default, `sections`, `summary`, `tokens`), so the prompt renderer and the tool read identical values and cannot disagree about a default. `splitSections()` splits at the **shallowest heading level the document actually uses**, not at a fixed level: `support-bundle.md` is written entirely in `###` and would otherwise yield no sections, while `service-management.md` nests `###` under `##`, where splitting on both would tear one argument into three fragments. Code fences are skipped — several references embed shell blocks whose comments start with `##`. `MAX_DOC_TOKENS = 6_000` warns at load (largest today: `gpudb-conf` at ~3,300).
- **`src/knowledge/KnowledgeStore.ts`** — `createKnowledgeStore(docs)`, the in-memory analogue of `bundle/BundleSource.ts`. `get()` resolves ids **tolerantly** (case, whitespace, a `.md` suffix), which is what lets the ~9 existing prose cross-references inside documents ("see `service-management.md`") keep working with no corpus edits — the agent reads that spelling and passes it straight to the tool. `getSection()` prefers an exact heading match over a substring one, so a document holding both "Rules" and "Reporting Rules" resolves "Rules" correctly.
- **`src/tools/knowledge/`** — `kinetica_knowledge_read(id, section?)`, registered in **every** session (knowledge is capability-agnostic) and allow-listed, so it never hits the approval gate: a prompt in front of a mandatory read is a prompt the agent routes around. **It deliberately bypasses `applyOutputPipeline` on success** — that pipeline ends in `truncateOutput` (head 150 + tail 50 lines), which would silently delete the middle of any document over 200 lines, and `gpudb-conf.md` is already 165. Failures still go through it, so errors read like every other tool's. A section miss returns the section list rather than the whole body: the agent asked for less. There is no `catalog.ts` guard here (unlike `tools/bundle/` and `tools/observability/`) because this tool's prompt surface is the Knowledge Library section, built from the store itself.
- **`src/agent/prompt-sections.ts`** — renders inline bodies in the original `**Title:**` format and on-demand documents as card tables, with `forceInline` for the conditional bundle-reference case. `buildKnowledgeLibraryIntro()` explains the tool and states that triggers are requirements.
- **Protocol hooks, not hints** — every mandatory read hangs off a step the agent is already executing: Round 1 (matching playbook cards, in the same batch as the sweep), Round 2 (catalog references before those queries), Round 4 step 0 ("Read first, then propose"), Evidence Gap Handling (`version-quirks-7.2` before an unexpected retry), and Fix Instructions (`service-management` before any remediation that touches a service). This follows the lesson already recorded in the Observability section: **a capability described conditionally is a capability the agent will not use, and retrieval that depends on the model noticing relevance will be skipped — retrieval tied to a protocol step it is already executing will happen.**
- **An inline document must not answer the on-demand document's question** — measured 2026-09-16. `mutation-safety` (the one `disclosure: inline` document) carried a copy of the sanctioned restart commands (`systemctl stop gpudb` then `systemctl start gpudb`), and in a memory-pressure investigation the agent emitted them verbatim in a fenced Remediation step having never read `service-management` — despite **three** explicit prompt hooks ordering that read (`system-prompt.ts:135`, `:378`, and the bundle prompt's own). A copy sitting in always-present context satisfies the need the trigger exists to create, so the trigger has nothing left to pull toward; the hooks were already as pointed as wording gets, which is why the fix was removing the ANSWER rather than writing a fourth hook. `mutation-safety` now orders the read and keeps only the prohibitions (never `gadmin`, never a bare "restart the database"), so a skipped read leaves the agent **without** commands rather than with a partial copy — the failure mode then being a missing step rather than an invented one. Cost: **+17** prompt tokens. `src/knowledge/corpus.test.ts` pins `mutation-safety` free of `systemctl`. The rejected alternative was `disclosure: inline` for `service-management` (+1,427 tokens, max config 13,815 → 15,243, guaranteed by construction — but it makes the retrieval eval's assertion 3 permanently unsatisfiable, since an inlined document is never fetched with `kinetica_knowledge_read`, so it would have to be replaced by an outcome check).

- **`src/knowledge/corpus.test.ts`** — the only test that reads the real `knowledge/` tree. Asserts every document has ≥ 1 keyword (the standing guard for the Prettier bug below), every on-demand reference has an authored `summary`/`read_when` within limits and phrased as a trigger, ids are unique, every `<name>.md` mentioned in a body resolves, no document exceeds `MAX_DOC_TOKENS`, every playbook has `## Symptoms`, and that each document still carries its hard-won rules (moved here from `system-prompt.test.ts`, where a card summary could accidentally satisfy a body assertion).

**The Prettier/parser trap (fixed).** `parseFrontmatter()` walked the YAML block line by line, so a `keywords:` array that Prettier reflowed past `printWidth: 100` parsed as **empty** — 7 of the 12 references loaded with zero keywords and nothing failed, because nothing consumed keywords yet. `foldContinuations()` now folds continuation lines into the key above them before the key/value split, and `unquote()` strips surrounding quotes so a value may contain `: ` (which `summary` values do, and which is invalid unquoted YAML). Do **not** "fix" this by adding `knowledge/` to `.prettierignore`: multi-line arrays are valid YAML and a hand-authored one would still break.

### Evals (`src/evals/`)

Model-output eval harness, deliberately separate from unit tests. Runs the full agent loop (real Anthropic API) against a mocked `KineticaSession`. Two evals today: `report-format` asserts the generated report conforms to `knowledge/templates/report.md`, and `knowledge-retrieval` asserts across **three scenarios** that the agent actually reads the knowledge documents its cards oblige it to read.

- **`mock-session.ts`** — `createMockSession()` returns a `KineticaSession` backed by canned `Response` objects. DB-engine endpoints use the double-encoded `data_str` envelope (port 9191); host-manager endpoints return plain JSON (port 9300). Unknown endpoints return empty success so the agent doesn't crash on unmocked probes. The `/admin/show/shards` response uses the real `{shard_array_version, shard_map}` schema consumed by `summarizeShards()` — not the raw 16k array. `createStaleRankSession()` and `createUnappliedConfigSession()` are the two worlds built to exercise the `service-management` trigger — a rank that is down (restarting IS the investigation) and a config value written but unapplied (the restart is INCIDENTAL to a throughput investigation). Both live here rather than in the `.eval.ts` file because vitest excludes `*.eval.ts`, so a wrong endpoint key would otherwise surface only on a paid run.
- **`capturing-save-report.ts`** — Drop-in replacement for `makeSaveReportTool()` that captures report content in memory instead of writing to disk.
- **`dump-report.ts`** — `dumpEvalReport()` writes a run's captured report to `reports/eval-<scenario>-<pass|fail>-<UTC timestamp>.md` (gitignored, scrubbed via `scrubCredentials()`), prefixed with a `---` frontmatter block recording outcome, turns, cost, tool calls and the knowledge ids read; `preserveRunArtifact()` announces the path instead of printing the body. Failures were the original motive — a failing CONTENT assertion cannot be diagnosed from the log, and three times the verdict turned entirely on report text that lived only in terminal scrollback. **Passes are written for the mirror-image reason:** a green run is the evidence a fix WORKED, and discarding it leaves "did the trigger fire, or did the scenario pass vacuously?" with no artifact to answer it. The outcome is in the filename so a directory listing needs no opening, and the frontmatter makes each artifact self-describing rather than dependent on its log line. Never throws, and the fallback differs by outcome: a FAILING run's body is printed when the write fails (a human is about to reason over it), a PASSING run's is not (a wall of text on every green run is how the stderr copy stopped being read). A dump must never turn an assertion failure (exit 1) into a harness failure (exit 2).
- **`report-assertions.ts`** — Pure validators for the report markdown: top-level heading, required sections in canonical order (`REQUIRED_SECTIONS`, which includes `## Timeline`), metadata labels. Tested in `report-assertions.test.ts`.
- **`report-format.eval.ts`** — Entry point. Reuses `MCP_SERVER_NAME` and `makeUserMessage` exported from `agent/run-agent.ts` so the eval can't drift from prod config. It passes no `allowedTools`: its `autoAllow` callback already approves everything, so listing them would only duplicate the decision and re-introduce the SDK-side shadowing prod now avoids. Exit codes: `0` pass, `1` assertion failed, `2` harness failure.
- **`knowledge-assertions.ts`** — Pure validators for knowledge RETRIEVAL: which ids were read, whether a read preceded `save_report`, whether a service-touching remediation read `service-management`, whether the report emits a `gadmin` service command, and whether the report names the ids it read. Both content checks key off what the agent TELLS the operator, never off a bare word match — each fired on a CORRECT report before it was fixed. `gadminCommandLines()` flags a gadmin command inside a code fence or on a prose line that does not disown it, so a report passing the never-emit table on to the operator (the corpus working) is not a failure; `TOUCHES_A_SERVICE` matches verb-then-object ("restart the database") rather than the restart caveat `mutation-safety.md` obliges every config change to carry ("a DB restart to take effect"). Tested in `knowledge-assertions.test.ts`.
- **`knowledge-retrieval.eval.ts`** — Entry point for the retrieval eval (`npm run eval:knowledge-retrieval`). Progressive disclosure traded a guarantee for a trigger: with bodies inlined the agent could not fail to have the rules in context; with cards it must choose to fetch them. Unit tests prove the card renders; only a real model run proves it is acted on. The issue text matches the `memory-pressure` card's symptom line, so the eval measures whether a MATCHED card is acted on — not whether the model can guess relevance. Assertions are structural (did a read happen, is `gadmin` absent), never about wording, because wording assertions flake on model non-determinism.

**Important conventions:** Eval files use the `*.eval.ts` suffix so vitest's `src/**/*.test.ts` glob skips them. `npm test` never runs evals; use `npm run eval`. See `src/evals/README.md` for the design rationale and how to add scenarios.

### System Prompt (`agent/system-prompt.ts`)

Pure function `buildSystemPrompt()` constructs the agent's instructions including: 5-round investigation protocol (3 diagnostic rounds + Round 4 mutation proposal + Round 5 post-mutation verification), diagnostic tool descriptions, Kinetica domain knowledge (system tables, failure patterns), the knowledge library (playbook and reference **cards**, plus the bodies of any document marked `disclosure: inline` — today `mutation-safety`, which supplies the Mutation Safety Rules block, and `support-bundle` when a bundle is attached), analysis rules (named hypotheses, evidence-tied conclusions, and the **One Time Axis** rule — present in both prompts — that forbids equating or ordering events from different clocks unless both are UTC or the offset is known, routing an unknown offset to Evidence Gaps rather than a guess), and a report template placed at the end (recency bias).

The report's **section order is declared once — in `knowledge/templates/report.md`** — and `agent/report-template.ts` derives `REPORT_SECTIONS` / `REPORT_SECTION_ORDER` from its `##` headings; both prompt builders render the `**Section order:**` line from that constant. This is not decoration. The order used to be written out in prose _beside_ the injected template, and the two drifted: the commit that added `## Timeline` to the template (2026-09-03) left the prose list untouched, so the prompt shipped a template containing Timeline next to a **CRITICAL** prose list that omitted it and said "Do NOT reorder sections". Nothing failed for two weeks because Sonnet 4.6 resolved the contradiction in favour of the template; when the SDK upgrade moved the `sonnet` alias to Sonnet 5 (above), it followed the CRITICAL prose instead and **all three knowledge-retrieval eval scenarios failed** — one omitted Timeline, two emitted it outside the enumerated order. `report-template.test.ts` now pins the derived list against the template AND against the eval's `REQUIRED_SECTIONS`, the third declaration. The general lesson, and it is the same one the observability section records: **two specifications of the same thing in one prompt is a bug even while it passes — which one wins is decided by the model, not by you.**

The prompt composes four extracted sources, each owned by a separate module so the builder does not grow with tool or corpus count:

- `src/tools/catalog.ts` — `TOOL_CATALOG: Record<ToolName, CatalogEntry>` plus `buildEvidenceChecklist()` which renders the prompt's Evidence Checklist table. Because the catalog is typed as a full record over `DIAGNOSTIC_TOOL_NAMES ∪ MUTATION_TOOL_NAMES`, **adding a tool to either tuple without a corresponding catalog entry is a typecheck error** — new tools cannot ship invisible to the agent.
- `src/agent/time-axis-section.ts` — `buildTimeAxisSection(context, observability?)`, the **One Time Axis** rule, shared by BOTH prompt builders exactly as `buildObservabilitySection` is. Written inline in the two builders it drifted on the very commit that added it (the live copy dropped the "bundle records no UTC offset" fact that makes an unknown offset actionable, and asserted Prometheus/Loki UTC unconditionally), and two separate tests pinned the two variants, so the divergence would have been locked in rather than caught. The stats-stack clause is gated on the endpoint actually reached, like every other claim about that stack.
- `src/agent/prompt-sections.ts` — `buildFailurePatternsSection()`, `buildReferenceSection()` and `buildKnowledgeLibraryIntro()`, shared by BOTH prompt builders. This is where the inline-vs-card decision is executed; the builders' signatures are unchanged, because the renderer derives the tier from each document's own `disclosure`. See Progressive Disclosure above.
- `src/agent/report-template.ts` — loads `knowledge/templates/report.md` at import time and exports it as a string. `console.warn` surfaces load failures rather than silently shipping an empty template. Keeps `buildSystemPrompt()` pure.
- `knowledge/templates/report.md` — the diagnostic report Markdown skeleton injected at the end of the system prompt. Edit this file to reshape the report format; no code change needed. Its `## Timeline` section (between Evidence Collected and Evidence Gaps) is the one place events share an axis, and that axis is UTC: each row names its source and the stamp as observed with its zone, an unconvertible host-local stamp gets `unknown` in the UTC column and the missing offset goes under Evidence Gaps, and events from different clocks are never ordered unless both are UTC or the offset is known.

### Prompt Budget Tripwire (`agent/prompt-budget.ts`)

The always-on part of the system prompt — the tool catalog, SQL examples, protocol text, and now one **card** per knowledge document rather than every body — is assembled once at startup. This module makes that cost _visible_ before it gets expensive. Pure, dependency-free, never throws:

- `estimateTokens(text)` — `chars / 4` heuristic, rounded up (a tripwire needs to be _present_, not _precise_; swap for a real tokenizer behind the same signature if exact counts ever matter)
- `checkPromptBudget(prompt, opts?)` — returns an immutable `BudgetReport` (`tokens`, `chars`, `threshold`, `overBudget`); comparison is strictly-greater, so a prompt exactly at the threshold is not flagged
- `DEFAULT_PROMPT_BUDGET_TOKENS = 18_000` — warn threshold (a tripwire, not a hard limit; 15_000 → 20_000 on 2026-06-03, 20_000 → 30_000 on 2026-09-01, then **lowered 30_000 → 18_000 on 2026-09-12** when progressive disclosure moved the document bodies out of the prompt — the first change driven by a design change rather than corpus growth; each step is recorded in the constant's doc comment)

Wired into `runAgent()` immediately after `buildSystemPrompt()`: a `DEBUG`-gated size line plus an **unconditional** over-budget warning to stderr, cueing a check for documents marked `disclosure: inline` that could be on-demand and for cards whose summaries have grown. Measured 2026-09-16, 6 playbooks + 11 references + 1 bundle reference, after progressive disclosure and after the save-consent widget (**+99** tokens on every live prompt, **+164** bundle-only — the rewritten Post-Report Behavior section). The right-hand column is the 2026-09-12 measurement it replaced; the pre-disclosure figures those in turn replaced are recorded above and in the paragraph below.

### Session Budget Guard (`agent/session-budget.ts`)

Caps per-session spend. The SDK's `maxBudgetUsd` is the source of truth for the hard cutoff, but it only reports the true dollar figure on the _final_ result message — so this module estimates running cost from per-turn token `usage` to warn the operator _before_ the cap fires. Like `prompt-budget.ts`, it's a tripwire, not an accountant. Pure functions + closure-based factory; never throws (bad token counts degrade to 0).

- `resolveMaxBudgetUsd(flag?, env?)` — resolves the cap: `--max-budget` flag > `ADMIN_AGENT_MAX_BUDGET` env > `DEFAULT_MAX_BUDGET_USD` ($5.00). Invalid values (≤ 0, non-finite, non-numeric) are ignored so a bad env var degrades to the default.
- `createBudgetTracker({ maxUsd, warnFraction? })` — accumulates estimated spend; `shouldWarn()` fires once when spend strictly exceeds `warnFraction * maxUsd` (default `DEFAULT_WARN_FRACTION` = 0.8), `markWarned()` makes it one-shot.
- `estimateTurnCostUsd()` + `MODEL_PRICING` — price one turn's usage from a per-model, per-MTok table (estimate only).
- `fromSdkUsage()` — normalizes the SDK's snake_case `usage` shape into `TokenUsage`.

Wired into `runAgent()`: the budget is resolved in `cli/index.ts` and threaded through `RunAgentOptions.maxBudgetUsd`. A startup line shows the guard (`Budget guard: $X.XX (raise with --max-budget)` for API-key billing, or `subscription (Pro/Max) — turn-limited` for OAuth). On hitting the cap the session ends with `error_max_budget_usd` framed as a safety limit, not a crash.

### Credential Security

- `KineticaSession.ts`: credentials captured in closure, unreachable from outside; 30s request timeout (`REQUEST_TIMEOUT_MS`) via `AbortSignal.timeout()`
- `session/env-file.ts`: `.env` save offer writes only `KINETICA_URL` and `KINETICA_USER` — password is never persisted to disk
- `report/scrub.ts`: defense-in-depth scrubbing of URLs, auth headers, passwords from saved reports
- `tools/audit-redact.ts`: redacts mutation-tool inputs in the stderr audit log. Pattern-based stripping for inline SQL credentials (`PASSWORD '...'`, `IDENTIFIED BY '...'`) plus sha256 fingerprinting for known-sensitive keys and any string >300 chars. Prevents `config_string` payloads (full gpudb.conf with license keys, LDAP binds, TLS material) from leaking to logs.
- `approval/gate.ts`: three-response approval protocol (y/n/explain) wired as `canUseTool` callback — triggers for mutation tools not in the diagnostic allow-list
- `approval/registry.ts`: per-tool approval policy registry; diagnostic tools registered read-only, mutation tools default-deny
- `approval/display.ts`: terminal formatting for approval prompts

## Key Patterns

- **Immutable data**: `readonly` on all type fields, `ReadonlyMap`, frozen objects (`TurnGate`), reduce-based construction
- **Discriminated unions**: `ToolResult<T>` narrows on `ok` field; `ResolveUrlResult` narrows on `ok`; `ApprovalResponse` is `"allow" | "deny" | "explain"`
- **Factory functions over classes**: `createSession()`, `createRegistry()`, `createTurnGate()`, `createApprovalGate()`
- **Graceful degradation**: `discoverCatalogSchemas()` returns `undefined` on any error; `diagnostic-sql.ts` builders have `fallback` constants
- **Co-located tests**: every `.ts` has a sibling `.test.ts` in the same directory
- **`BUILDER_REGISTRY`**: data-driven registry in `diagnostic-sql.ts` mapping 18 system tables to SQL builder functions + fallbacks + prompt section headings

## Kinetica API Quirks

- `/execute/sql` returns double-encoded JSON: outer `data_str` contains `json_encoded_response` as a string that must be parsed again — the SQL `executeSql()` handles this; REST tools use `parseDataStr()` from `tools/rest/parse-data-str.ts`
- Column names come from `column_headers` array, not from the JSON keys (which are `column_1`, `column_2`, etc.)
- `ki_catalog.ki_columns` uses `column_type_oid` (not `data_type`), `is_dict_encoded` (not `dict_encoding`), `bytes_on_disk_compressed`/`bytes_on_disk_uncompressed` (not `compression_type`)
- REST endpoints also return double-encoded `data_str` — always use `parseDataStr<T>()` rather than raw `JSON.parse()` to handle edge cases safely
- Shard key columns cannot be altered in-place — once designated at table creation, the shard key column definition is immutable (Kinetica 7.2 limitation)
- `ki_catalog.ki_tables` and `ki_catalog.ki_version` do NOT exist in Kinetica 7.2.x — use `ki_objects` and `/show/system/status` respectively
- `/admin/show/logs` is not implemented in 7.2.x — returns 404 "Unknown URI"
- `/admin/show/configuration` and `/admin/alter/configuration` are host manager endpoints (port 9300) — use `makeRequestToPort()` with `data_str` double-encoding; response contains `config_string` (full gpudb.conf)
- `/alter/system/properties` is **not** an in-memory runtime change — it **edits `/opt/gpudb/core/etc/gpudb.conf` in place** (line-level, verified by md5 + mtime + the changed line) and mirrors to `persist/gpudb/rank-0/gpudb.conf.bak` (a mirror holding the NEW value, not a rollback point). `/show/system/properties` then reports the file, so `verification: confirmed` means **persisted**, not applied. The running process does not re-read: `tps_per_tom` 4→8 changed zero threads on either rank (98/98, 90/90 under load), and `enable_audit=TRUE` with content flags on produced no audit output. Effect comes on restart. `kinetica_alter_configuration` (host manager :9300) writes the SAME file — never use both routes in one session. `enable_procs` and `worker_endpoint_threads` are rejected by the endpoint (`is not a valid parameter`); `sm_omp_threads`/`kernel_omp_threads` do not exist. `/show` also dot-sections names `/alter` flattens (`ai_api_url` ↔ `conf.ai.api.url`) — 12 of the 43 are reachable only via that normalisation, and 7 of the 43 are absent from `/show/system/properties`, so they can only ever return `not_reported` (4 of those are still in `gpudb.conf` — `/show` reports 306 keys, the file has 330, and neither is a superset — so `kinetica_show_configuration` is the authoritative read-back for them) — see `knowledge/references/gpudb-conf.md`
- `/show/system/properties` returns property names **`conf.`-prefixed** while `/alter/system/properties` takes them **bare** (296 of 306 keys carry the prefix; the exceptions are `version.*` and `system.font_families`). A read-back keyed on the bare name therefore finds nothing and looks like a no-op whether or not the write landed. `alterSystemProperties` had exactly this bug; use `lookupProperty()` (exact match, then `conf.`-prefixed, never a substring match) for any read-back. Be sceptical of any "the property didn't change" report that does not say which spelling it read.
- `/show/table` with empty `table_name` returns schema-level collections (not individual tables) with empty `sizes` array — use `ki_catalog.ki_objects` for table listing
- `/show/table` requires `<schema>.<table>` format — three-part names (e.g., `ki_home.ki_catalog.ki_objects`) return 400 error
- `/admin/rebalance` returns "Database must be offline" on single-worker-rank clusters — rebalance requires 2+ worker ranks
- `/admin/verifydb` returns `orphaned_tables_total_size: -1` on healthy systems (not 0) — -1 means "not checked"
- `/show/resource/objects` rank JSON structure is `{"objects": [...]}` — array nested under `objects` key, each with `locked` field (boolean)
- `/show/resourcegroups` default groups: `kinetica_system_resource_group` (priority 100), `kinetica_default_resource_group` (priority 50); includes `max_tier_priority` field
- Rank 0 is the head/coordinator node with minimal resources and no data tiers; worker ranks (1+) hold all data
- Host manager root endpoint (`/` on port 9300) returns plain JSON (no `data_str` encoding, no authentication required) — do NOT use `parseDataStr()`
- `ki_tiered_objects.id` is a string identifier (e.g., `@nyctaxi@365[col][0]`), NOT a numeric OID — cannot be joined with `ki_objects.oid`. For per-table tier placement, use `kinetica_resource_objects` with `table_names` filter
- `ANALYZE TABLE` is NOT supported by Kinetica — `/execute/sql` returns a syntax error. Kinetica does not maintain cost-based optimizer statistics the way PostgreSQL or Oracle do; query planning uses shard/column metadata already tracked by the storage layer. Do not suggest `ANALYZE TABLE` as a remediation or propose it via `kinetica_execute_mutation_sql` — there is no equivalent "refresh table stats" command to substitute.
