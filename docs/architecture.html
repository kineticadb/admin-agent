The map

One process, three neighbours

The agent is a single Node process that sits between an operator's terminal and three outside things: the Anthropic API, a live Kinetica cluster, and — optionally — an extracted support bundle on disk. Everything interesting happens inside that middle lane.

The most load-bearing fact about the lane is what it cannot reach. Bash, Edit, Write and MultiEdit are in the SDK's deny list, and deny beats every allow — so the model's only way to affect the world is through tools this codebase wrote and named.

Before the first prompt

Boot, and the one fork in it

Startup is deliberately ordered so the cheapest failure happens first. Flags are validated before any side effect; Anthropic auth runs before Kinetica credentials are collected, so a session with no plausible auth path dies before anyone types a password.

What gets assembled at the bottom of that funnel

Before the loop starts, runAgent runs four independent loads in parallel — catalog schema discovery (skipped without a live engine), playbooks, references, and bundle references — then builds one system prompt and checks its size. Bundle references load in every session, even one that never attaches a bundle, because the prompt is built once and a mid-session kinetica_load_bundle would otherwise drive those tools blind.

The core mechanism

One prompt, end to end

Type "queries are timing out on rank 3" and two loops start turning. They meet at the model, and they run at different speeds: the outer turn loop ticks once per operator sentence; the inner tool loop may spin a dozen times inside a single turn without the operator ever getting the prompt back.

What keeps them from colliding is a 45-line primitive: the TurnGate. It is a promise that the prompt generator awaits and the message loop resolves — closed when a message is yielded, opened only on stop_reason: "end_turn". Open it on tool_use instead and the operator would be asked for input in the middle of the agent's own investigation.

  1. The generator yields makeInteractivePrompt is an async generator the SDK pulls from. It wraps your text in an SDKUserMessage, calls turnGate.close(), starts the spinner, and yields.
  2. The model reads a prompt it has seen before The system prompt — protocol, tool catalog, playbooks, references, report template — was built once at startup and is served from cache. A non-zero cacheReadTokens in the session summary is the proof.
  3. Tool calls fork on the allow-list A name in ALLOWED_TOOL_NAMES runs immediately. Anything else falls through to canUseTool, which renders the approval panel. The registry is default-deny, so a tool nobody thought to register prompts rather than runs.
  4. The approval loop only exits on y or n explain prints the model's stated reasoning and re-prompts; unrecognised input re-prompts silently. An aborted signal denies rather than hangs, and the denial message tells the model to skip and continue instead of retrying.
  5. Results are shrunk before the model sees them Kinetica's double-encoded data_str is parsed, reshaped into markdown, then cut to head 150 + tail 50 lines. Without that step a single shard map — 16,384 entries — would swallow the context window.
  6. Text streams out while tools still run includePartialMessages pushes text_delta events to a line-buffering aligner that holds back markdown table blocks until it can align the columns, and passes prose through immediately.
  7. Only end_turn hands the terminal back On tool_use the spinner restarts and the loop continues. On end_turn the gate opens and the generator wakes up to print "You:".
What the model is told to do

Five rounds, two of them optional

The loop in Figure 3 is mechanism; the protocol below is policy, written into the system prompt. Rounds 1–3 are diagnosis and always run. Rounds 4 and 5 only happen when the evidence supports a specific remediation, and Round 4 is the point where the approval panel from Figure 3 fires.

The rule that matters most is the one drawn dashed: after Round 3 the report is mandatory, gaps and all. An investigation that ends without a report is a failure mode, so the prompt closes that door explicitly.

Guardrails

What stops it going wrong

Each rail below is enforced in code rather than requested in the prompt — the distinction matters, because a prompt is advice and a deny list is not.

Rail How it is enforced Where
No shell, no file writes disallowedTools lists Bash, Edit, Write, MultiEdit — deny overrides every allow, including bypass modes agent/run-agent.ts
Mutations need a person Mutation tools are deliberately kept out of allowedTools so they fall through to the approval gate. No wildcard is ever used in that list approval/gate.ts
Unknown tools prompt The read-only registry is default-deny: only names explicitly registered bypass the gate, so a newly added tool prompts until someone registers it approval/registry.ts
Context blowup Every tool result passes formatOutput → truncateOutput; the 16,384-entry shard array is summarised per rank before it is ever formatted output/truncate.ts
Runaway spend maxBudgetUsd is passed to the SDK only under API-key billing; a token-usage estimate warns once at 80% so the cutoff is never a surprise agent/session-budget.ts
Runaway turns 100 turns with a live session, 40 bundle-only — the guard for subscription users, who have no meaningful dollar cap agent/run-agent.ts
Prompt bloat checkPromptBudget() warns past 20k tokens; the corpus currently sits near 17.2k agent/prompt-budget.ts
Credential leakage Credentials live in a closure; the password is never written to .env; reports are scrubbed and mutation audit lines redact config payloads report/scrub.ts · tools/audit-redact.ts
Bundle path escape The index drops symlinked leaves and any entry whose realpath leaves the bundle root — and every reader draws from that one index bundle/bundle-index.ts
The composability point

A live connection and a support bundle are capabilities, not modes. A session can hold either or both, and the tool set is their union — which is what lets the agent read what a rank logged at 03:14 last Tuesday and then check whether that condition still holds right now. Bundle tools are always registered against a lazy holder, so kinetica_load_bundle can attach one mid-conversation even though the SDK fixed the tool set when query() was created.
